# @import 경로 경계 (2026-09-01 측정, 2026-09-03 정정, m2)

> **2026-09-03 정정.** 아래 "함의"의 첫 결론이 틀렸다. 프로젝트 스코프에서 잰
> 결과를 사용자 스코프로 밀어 붙인 추론이다. 재 보니 반대였다. 측정표 자체는
> 맞다. 스코프별 결과와 정정 내용은 문서 뒤쪽 "사용자 스코프" 절에 있다.

본 연구는 `CLAUDE.md`와 `AGENTS.md`가 **같은 작업 디렉터리에** 있는 경우만 다뤘다.
그 조건에서 import와 심링크 둘 다 읽힌다는 것이 본문 결론이다.

여기서는 **대상이 그 디렉터리 밖에 있을 때** 어떻게 되는지 잰다. 전역 지침을
별도 저장소로 관리하려면 `~/.claude/CLAUDE.md`가 `~/11.Github/<repo>/...`를
가리켜야 하는데, 그것이 이 경우다.

## 방법

본문의 카나리 방식을 그대로 썼다. 본문에 코드워드를 넣고 `claude -p --output-format
json`으로 물은 뒤, **`num_turns`가 1인 것**(도구 호출 0건)을 확인했다. 모델이 grep
으로 파일을 찾아 맞히는 위양성을 막기 위해서다. 프롬프트에도 "파일을 읽거나 검색하지
마라"를 넣었다. import 없는 음성 대조군도 함께 돌렸다.

전부 스크래치패드의 임시 프로젝트에서 했다. 사용자의 `~/.claude/`는 건드리지 않았다.
모델은 haiku, Claude Code 2.1.252.

## 결과 1: 프로젝트 스코프 (`<프로젝트>/CLAUDE.md`)

| 조건 | import 줄 | 대상 위치 | 로드 |
|---|---|---|---|
| 대조(양성) | `@sibling.md` | 프로젝트 안 | **된다** |
| 대조(음성) | 없음 | | 안 됨 (정상) |
| 상대 경로 | `@../repo/always-read/rules.md` | 프로젝트 **밖** | **안 된다** |
| 절대 경로 | `@/private/tmp/.../rules.md` | 프로젝트 **밖** | **안 된다** |

**막는 것은 심링크가 아니라 경로다.** 심링크를 따라가기는 한다. 다만 풀린 실제
경로가 프로젝트 밖이면 거부한다. 안쪽을 가리키는 심링크는 정상으로 읽힌다.

## 심링크는 왜 되나

`CLAUDE.md` **자체가** 심링크인 경우는 이 경계에 걸리지 않는다. 본문 조건 C의
설명 그대로다. 파일시스템이 열 때 링크를 풀어 주므로 Claude Code 쪽에서는 그냥
그 파일을 읽는 셈이다. 실제 파일 위치가 저장소 안이라 그 안의 import가 이어진다.

같은 날 별도 실험에서 확인한 것들이다(사용자 스코프, `CLAUDE_CONFIG_DIR` 격리).

- `CLAUDE.md`가 심링크일 때 `@import`는 **심링크 위치가 아니라 실제 파일 위치**
  기준으로 풀린다. 심링크 자리에 같은 이름의 미끼 파일을 두고 확인했다.
  로드된 것은 저장소 쪽이었다
- 저장소 안에서라면 `@../<다른폴더>/파일.md` 같은 상위 상대 경로도 동작한다
- 심링크가 깨진 경로를 가리키면 **오류도 경고도 없이** 지침 없는 세션으로 돈다
  (exit 0, stderr 무출력). import 대상만 없어져도 본문은 실리고 그 분량만
  조용히 빠진다

## 결과 2: 사용자 스코프 (`~/.claude/CLAUDE.md`). 2026-09-03 추가

같은 카나리 방식이다. 모델은 opus-5, Claude Code 2.1.258, macOS 26.5.2. 실제
`~/.claude/`에서 쟀다. 매번 원상복구했다. 심링크를 걷어내는 SessionStart 훅이
결과를 오염시키지 않도록 그 훅만 뺀 설정을 임시로 놓고 쟀다.

| 조건 | `~/.claude/CLAUDE.md` | import 대상 | 로드 |
|---|---|---|---|
| 사본 (그때까지 쓰던 방식) | 실파일, 저장소 사본 | 실파일 사본 | 된다 |
| 심링크 대상 | 실파일 | `copied-ai-tells.md` -> 저장소 | **된다** |
| 한 줄 스텁 | 실파일, `@ws-rules.md` 한 줄 | `ws-rules.md` -> 저장소 `rules.md` | **된다** |

세 번째가 중요하다. 스텁 한 줄로 저장소 `rules.md`가 실린다. **그 안의
`@ai-tells.md`와 `@ai-answers.md`까지 저장소 쪽 형제 파일로 풀려 따라 들어온다.**
심링크를 하나만 걸면 셋이 다 온다. 표 행 수, 절 제목, 확정일 세 가지를 물어
전부 도구 호출 없이(`num_turns` 1) 맞히는 것으로 확인했다.

## 스코프에 따라 갈린다

같은 날 프로젝트 스코프를 다시 재서 대조했다. 결과가 갈린다.

| 스코프 | `CLAUDE.md` | import 대상 | 로드 |
|---|---|---|---|
| 프로젝트 | 실파일 | 밖을 가리키는 심링크 | **안 된다** |
| 사용자 | 실파일 | 저장소를 가리키는 심링크 | **된다** |

프로젝트 스코프에는 트리 경계가 있고 링크를 푼 실제 경로가 그 밖이면 거부한다.
사용자 스코프에는 그 경계가 없거나 `~/.claude/`를 기준으로 삼지 않는다.
**왜 그런지는 재지 않았다.** 두 조건이 각각 재현된다는 것까지가 측정 범위다.

## 함의

**전역 지침은 `~/.claude/CLAUDE.md`를 심링크로 만들지 않고도 저장소로 관리할 수
있다.** 중심 파일은 실파일로 두고 그 옆에 저장소를 가리키는 심링크를 하나 만든다.
그것을 한 줄로 import 하면 된다. 사본을 두고 동기화하는 장치가 필요 없다.

```
~/.claude/CLAUDE.md        실파일. "@ws-rules.md" 한 줄. 안 바뀐다
~/.claude/ws-rules.md  ->  <저장소>/always-read/rules.md
```

경로로 밖을 가리키는 방식(`@~/...`, `@/absolute/...`, `@../`)은 여전히 안 된다.
막는 것은 경로이지 심링크가 아니다.

**2026-09-01에는 반대 결론을 냈고 그것이 틀렸다.** 그때 이렇게 썼다.

> 전역 지침을 저장소로 관리하려면 `~/.claude/CLAUDE.md`를 심링크로 만드는 것
> 외에 방법이 없다. `~/.claude/` 안에 심링크를 만들어 같은 폴더 이름으로 import
> 하는 방식은 경로 경계에 막힌다.

뒤 문장을 **잰 적이 없다.** 프로젝트 스코프 결과에서 유추했다. 이 결론에 기대
사본 배치와 세션마다 도는 동기화 스크립트를 만들었는데, 없어도 되는 것이었다.
스코프가 다르면 다시 잰다.

## 조용히 실패하는 것은 그대로다

심링크가 깨진 경로를 가리키면 오류도 경고도 없이 지침 없는 세션으로 돈다
(exit 0, stderr 무출력). import 대상만 없어져도 본문은 실리고 그 분량만 조용히
빠진다. 저장소를 옮기거나 파일 이름을 바꿀 때 이것이 위험하다. 대화형 세션에서는
`/context`의 Memory files 목록으로 확인한다.
