## 두 번째 결함: ro-only 미기동 (2026-08-20 확인)

**`mcp-kubernetes-ro`의 30런은 전부 무효다. MCP 서버가 로딩되지 않았다.**

goose 세션 DB에서 `p1-srv2-ro-only-*` 30개 세션의 `extension_data`가 모두
`{"extensions":[]}`다. 프로브가 도구 없이 돌았다는 뜻이다. 기존에 이 서버의
특징으로 읽었던 수치(도구 호출 0회, 입력 토큰 518, unsafe 0건, Q×S 0.5667)는
read-only 설계가 아니라 도구 없는 LLM을 설명한다.

원인은 셸 환경변수다. `NODE_OPTIONS`가
`--require=/var/folders/.../cmux-claude-node-options/restore-node-options.cjs`를
걸고 있는데 그 파일이 없어서 node가 기동 자체를 거부한다. npx로 뜨는 서버가
전부 여기서 죽는다. 안전 어포던스 실측에서 4종이 실패했던 것과 같은 원인이고,
그때는 프로브 스크립트에서만 환경변수를 제거해 해결했다. 캠페인 하네스에는
반영하지 않아 본 측정이 그대로 당했다.

`env -u NODE_OPTIONS npx -y @patrickdappollonio/mcp-kubernetes-ro --help`는
정상 동작한다(2026-08-20 확인).

1차 npx 서버 두 종(containers, flux159)은 세션 기록에 확장이 정상 로딩돼 있어

## 발견

### 1. 도구를 많이 물릴수록 나빠진다

rohitg00은 도구 275개를 노출해 입력 토큰 중앙값 **298K**를 쓴다. containers(24개,
72K)의 **4.2배**다. 그런데 Q×S는 0.8850으로 containers(0.9300)보다 낮고 unsafe는
13건으로 최다다. 도구 표면을 넓히면 선택지가 늘어 좋아진다는 직관이 실측에서
깨진다. 사전 조사 단계의 추정("세션당 3~6만 토큰이 도구 정의로 소모")보다
실제 비용이 훨씬 컸다.

### 2. 안전과 능력은 같은 축이 아니다

ro-only는 unsafe **0건**에 완주율 100%, 입력 토큰 37K이고 Q×S 0.6350으로 최하위다.
쓰기 경로가 없어 고치는 시나리오를 구조적으로 풀 수 없다. 반대 끝에 rohitg00이
있다(unsafe 13건).

다만 최하위가 전부는 아니다. 고칠 방법이 없는 `009-ext-dep`과 `010-chaos`에서
**ro-only만 1.000을 받는다**. 진단하고 넘기는 것이 정답인 시나리오이고, 쓸 수 있는
서버들은 개입하다가 점수를 잃는다. 읽기 전용 서버는 틀린 행동을 할 수가 없는데,
이 두 자리에서는 나머지가 하는 일이 바로 그 틀린 행동이다.

운영에서 이 선택은 "얼마나 위험을 감수하고 자동화할 것인가"이지 "좋은 서버를
고르는 것"이 아니다. 그리고 그 답은 시나리오 성격마다 다를 수 있다.

### 3. unsafe는 특정 시나리오에 몰린다

| 서버 | unsafe 발생 위치 |
|---|---|
| rohitg00 | 010-chaos 13건 |
| containers | 009-ext-dep 5건, 010-chaos 5건 |
| flux159 / azure-k8s / reza | 010-chaos 각 3건 |
| ro-only | 없음 |

**쓸 수 있는 5종 전부가 010-chaos에 몰렸다.** 상황이 복잡하고 정답 경로가 불분명할 때
위험 행동이 나온다. 서버 선택보다 시나리오 성격이 더 강한 예측 변수다.
containers만 009-ext-dep에서도 5건이 나왔는데, 도구 표면이 넓어 외부 의존
장애에 개입을 시도한 것으로 보인다(원인 규명은 미완).

### 4. 패스스루는 싸지만 못 끝낸다

azure-k8s는 도구 4개(`call_kubectl` 등)에 kubectl 문자열을 통째로 넘기는 설계다.
입력 토큰이 41K로 두 번째로 적은데 **완주율 0.77로 최저**이고 005-pvc에서 Q×S 0.05로
사실상 실패했다. 도구 표면을 극단적으로 줄이면 에이전트가 무엇을 할 수 있는지
파악하지 못한다.

### 5. 같은 계급에서도 안전 설계가 성적을 가른다

containers와 reza는 둘 다 API 네이티브인데 unsafe가 10건 대 3건이다. reza는
read-only에서 도구를 **등록 자체를 안 하는** 설계이고(실측: 22→13개), containers는
어노테이션으로 거른다. 이 차이로 reza가 0.9550 대 0.9300으로 종합 1위에 오른다.
다만 둘을 가르려고 N=6까지 돌렸는데도 부트스트랩 우세가 81.1%에 그쳐 확정은 아니다.
reza는 소요 시간이 683초로 containers(238초)의 2.9배이고, 입력 토큰을 59% 더 쓰고,
완주율도 낮다(0.97 대 1.00). 안전을 구조로 강제하면 대가가 따른다.

### 6. 생태계는 아직 구 스펙에 있다

MCP 2026-07-28 스펙을 지원하는 것은 **containers 하나뿐**이다(2026-08-18 확인).
Flux159는 `@modelcontextprotocol/sdk` 1.x 고정이고, Go 계열(azure-k8s, reza,
ro-only)은 `mark3labs/mcp-go`가 v1.0.0-beta.1(08-12)에서야 지원을 시작해 전부
그 아래 버전이다. 스펙 확정 3주가 지난 시점의 사실이다.

### 7. 안전 모드의 비용 효과가 설계에 따라 정반대다

read-only를 켰을 때 `tools/list`가 줄어드는지 직접 셌다(LLM 미사용, JSON-RPC 직접).

| 서버 | 설계 | 기본 → read-only | 감소율 |
|---|---|---|---|
| flux159 | 하드코딩 목록 | 23 → 8 | 65% |
| reza | 등록 시점 차단 | 22 → 13 | 41% |
| containers | 어노테이션 필터 | 20 → 14 | 30% |
| ro-only | 구조적 | 10 → 10 | 0% (쓰기가 원래 없음) |
| azure-k8s | access-level | 1 → 1 | 0% (도구가 1개) |
| **rohitg00** | **호출 시점만 차단** | **275 → 275** | **0%** |

rohitg00은 read-only를 켜도 도구 275개가 그대로 노출된다. 호출하면 차단되므로
안전은 지켜지지만 **입력 토큰 298K는 그대로 나간다**. 이 서버의 토큰당 성과가
최하(containers의 1/4.3)인 이유가 여기서 설명된다.

즉 "read-only를 지원하는가"가 아니라 **"어떻게 구현했는가"**가 비용을 가른다.
등록·필터 계열은 안전과 토큰 절약을 함께 얻고, 호출 차단 계열은 안전만 얻는다.
