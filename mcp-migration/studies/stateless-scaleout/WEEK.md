문서화가 8/18~19로 밀리면서 일주일이 비었다. 무인으로 돌려 지금 약한 곳을 메운다.
사용자는 8/11~14 OSSummit과 MCP Dev Summit, 8/17 휴일로 부재한다.

## 지금 무엇이 약한가

발행 직전 상태의 데이터는 결론을 뒤집을 만한 문제는 없지만 세 가지가 걸린다.

첫째, **게이트웨이 결론이 기본 설정 하나만 보고 내려졌다.** W5에서 구 스펙이
게이트웨이 뒤에서 파드 교체 때 HTTP 500을 3,540건 냈고(직접 경로는 400이 667건)
이걸 "게이트웨이는 파드 교체를 악화시킨다"로 해석했다. 그런데 CRD를 열어 보니
`failureMode`가 있고 기본값 `FailClosed`가 "대상이 사라지면 세션 전체를
실패시킨다"이다. 대안인 `FailOpen`은 "실패한 대상을 건너뛰고 살아 있는 것으로
계속 서빙한다"이다. 즉 우리가 잰 것은 기본값의 동작이고, 설정으로 달라질 수
있다. 확인하지 않고 발행하면 agentgateway에 부당한 서술이 된다.

둘째, **하네스가 실패를 400과 404로만 센다.** 그래서 게이트웨이 경유는 세션
유실 0으로 보이는데 실제로는 500으로 3,540건이 실패했다. 계수 기준을 고치지
않으면 같은 착시가 다른 곳에서도 생긴다.

셋째, **표의 값이 3회 중앙값인데 셀이 2배 넘게 흔들린다.** W1에서 구 스펙
연결 재사용 레플리카 4를 13회로 늘려 보니 95.6~189.4rps였고, 3회로 낸
중앙값(119.2)은 분포의 아래쪽이었다. 다른 구 스펙 셀도 같은 상태일 텐데 3회씩만
쟀다.

## 실행 계획

순서대로 돌린다. 앞 단계 실패가 뒤를 막지 않게 각 단계를 독립으로 둔다.

### V1. 게이트웨이 failureMode 검증 (최우선)

W5의 결론이 설정 탓인지 구조 탓인지 가른다. 세 축을 교차한다.

- 구 스펙 x `FailClosed`(기본) x 파드 교체
- 구 스펙 x `FailOpen` x 파드 교체
- 구 스펙 x `sessionRouting: Stateless` x 파드 교체 (세션 고정이 원인인지 분리)
- 신 스펙 x `FailClosed` / `FailOpen` x 파드 교체

각 5회. 500 응답 본문도 캡처해서 게이트웨이가 무엇이라 말하는지 남긴다.

판정: `FailOpen`에서 500이 사라지면 결론은 "기본 설정이 그렇다"로 바뀌고 권고는
"게이트웨이를 쓸 거면 failureMode를 검토하라"가 된다. 그대로면 원래 해석이 맞다.

### V2. 하네스 실패 분류 개선

`session_loss`(400/404), `gateway_error`(5xx), `other`를 따로 센다. 기존 실행
데이터는 errors 필드에 원본이 남아 있으므로 재계산으로 확인 가능하다.

### V3. M1 전 셀 고반복

12셀(구/신 x close/reuse x replica 1/2/4)을 각 10회. 표의 모든 값을 3회
중앙값에서 분포로 바꾼다. 약 8시간.

### V4. 핸들 설계 x 파드 교체

M3는 구 스펙 echo와 신 스펙 HMAC만 쟀다. 파드 메모리 핸들은 파드가 죽으면 그
파드의 상태가 전부 사라지는 가장 극적인 경우인데 재지 않았다. mem/hmac/redis
각 5회.

### V5. Redis 의존성 장애

"Redis에 두면 된다"의 정직한 반대편. Redis 자체가 죽으면 어떻게 되는지 잰다.
외부 저장은 새 의존성을 들이는 선택이라는 것을 수치로 보인다.

### V6. 레플리카 6 확인점

1, 2, 4의 추세가 이어지는지 한 점 더. 유실률 이론값 (N-1)/N이 계속 맞는지 본다.
워커 CPU 여유를 먼저 확인하고 안 되면 건너뛴다.

### V7. 장시간 안정성

30분 연속 실행. 지금 측정은 전부 30초와 60초라 드리프트를 볼 수 없었다.

### V8. 튜토리얼 재현 검증

발행문이 재현 가능하다고 주장하므로 실제로 확인한다. 스냅샷 복원부터 문서에
적은 순서 그대로 재구축하고 동작까지 본다. 클러스터를 갈아엎으므로 **가장
마지막에** 돌린다.

## 2부와 3부 (2026-08-10 추가)

1부가 하루면 끝나서 남는 닷새를 채운다. 세 스크립트가 앞 것의 종료를 기다렸다가
이어서 돈다(`run_week.sh` -> `run_week2.sh` -> `run_week3.sh`).

### 2부 (`run_week2.sh`)

- **V1r 게이트웨이 재측정.** 1부 V1은 5xx에서 재초기화하지 않는 하네스로 재서
  세션을 잃은 워커가 남은 실행 내내 실패했다. 실패 건수가 4,000의 1/8 배수로
  찍힌 것이 그 증거다. 하네스를 고쳤으니 다시 잰다. 직접 경로 대조도 함께.
- **S1 sessionAffinity ClientIP 비교.** 지금 글에는 "구 스펙이면 스티키 세션을
  켜면 되지 않나"에 대한 답이 없다. 켰을 때와 껐을 때를 스케일아웃과 파드 교체
  양쪽에서 잰다. 단서: 부하 생성기가 호스트 한 대라 클라이언트 IP가 하나다.
  ClientIP를 켜면 트래픽이 전부 파드 하나로 몰린다. 기전은 선명해지지만 실환경은
  IP가 여러 개라 효과가 부분적이다. 발행문에 이 단서를 반드시 같이 적는다.

### 3부 (`run_week3.sh`)

여기부터 클러스터 구성을 건드린다. 되돌릴 수 있는 순서로 뒀다.

- **S3 경로 (b) Gateway API 구현체 경유.** 한계 절의 "측정하지 않았다"를 지운다.
  gateway-PoC의 nginx Gateway Fabric을 재사용하되 `KUBE_CONTEXT`를 명시해 넘긴다
  (기본값이 `gateway-PoC`라 안 넘기면 다른 클러스터에 깔린다). 측정 후 제거.
  agentgateway와 달리 MCP를 모르는 L7 프록시라 세션 개념이 없다는 것이 관심사.
- **S2 kube-proxy nftables 모드.** cni 연구에서 메모리 70% 절감은 쟀지만 세션
  유실 거동이 iptables와 다른지는 안 봤다. 전환 후 스모크가 실패하면 측정을
  건너뛰고 아래 V8이 원복한다.
- **V8 튜토리얼 재현 검증.** 문서에 적은 순서(기동 -> 스냅샷 복원 -> 빌드/적재 ->
  배포) 그대로 해 보고 최소 클라이언트와 캡처까지 확인한다. 스냅샷 복원이라
  S2의 변경도 함께 원복된다. 그래서 마지막에 둔다.

### 발행문 반영 방침

측정은 전부 하되 글에 다 넣지는 않는다. `sessionAffinity`는 논리 구멍을 메우므로
본문에 넣는다. nftables와 경로 (b)는 저장소와 README에 두고, 한계 절의
"안 쟀다"를 "쟀다"로 바꾸는 선에서 쓴다. 튜토리얼이 종합 보고서가 되면 안 된다.

## 4부 (`run_week4.sh`, 2026-08-10 추가)

3부까지가 계획했던 구멍 메우기였다면 4부는 외부 타당성 확인이다. 지금 모든

  따라 움직여야 한다. 우리 수치가 클라이언트 모양의 산물인지 프로토콜의

- **T3 장시간 창.** "구 스펙은 27~49rps"의 근거가 30초짜리 10회뿐이다. 30분 창

  신 스펙 3회를 대조로 둔다.
- **T1 워커 3대 토폴로지.** 레플리카 4를 워커 2대에 올리면 파드가 노드를

  섞여 있다. 워커를 3대로 늘려 같은 셀을 다시 재면 갈리고, 새로 세운 노드에서
  같은 수치가 나오는지(재구축 재현성)도 함께 확인된다.
  조인 토큰이 고정값인데 기본 TTL 24시간이라 만료됐다. 재생성부터 한다.
  측정 뒤 w3를 지우고 Vagrantfile을 되돌린다. **기준 환경은 워커 2대다.**

T1이 클러스터를 바꾸므로 마지막에 뒀다.

## 5부 (`run_week5.sh`, 2026-08-10 추가): agentgateway 스파이크

측정이 아니라 **연구 후보의 착수 게이트 확인**이다. 사전 조사 4건으로 만든
`_CANDIDATES/agentgateway-study.md`가 제안한 두 축을 실물로 검증한다. 결과는
`runs/week5-agentgateway-2026-08-10/FINDINGS.md`에 자동으로 쌓이고, 판정은 사람이
8/18 아침에 한다.

- **G1 도구 이름 화이트리스트가 강제되는가.** echo만 허용하는 정책을 붙이고
  get-sum이 막히는지 본다. tools/list에서도 사라지는지(목록 필터링) 별도 관심사.
- **G2 prefixMode 재작명이 우회가 되는가.** 소스에서 인가 필터링과 이름 재작명의
  순서를 다 확인하지 못했다. Conditional/Always/Never 세 모드에서 접두사 이름으로
  차단 도구를 불러 본다.
- **G3 인자 기반 정책이 정말 표현 불가능한가.** 조사의 핵심 발견 후보다.
  `mcp.tool.arguments.a == 1` 조건을 넣어 보고 정책이 거절되는지, 수용되지만
  조건과 무관하게 통과하는지, 아니면 조건대로 갈리는지(= 조사가 틀림) 가른다.
- **G4 정책 지연 오버헤드.** 규칙 0개, 1개, 21개로 A/B.
- **G5 traceparent 전파.** 스펙이 `_meta`에 W3C Trace Context를 예약했는데
  게이트웨이가 잇는지 문서에 없다. 탭 프록시를 게이트웨이 뒤에 두고 확인한다.

구현 메모 두 가지.

3부의 재현 검증이 스냅샷을 복원하며 agentgateway를 지우므로 5부는 재설치부터 한다.

G5용 탭 프록시(`k8s/tap-proxy.yaml`)는 b-server를 고치지 않으려고 넣었다. SDK
2.0.0에서 도구가 요청 컨텍스트를 받는 방법을 찾지 못했다(`Context` 타입 주입은
pydantic 스키마 생성에서 막히고 `get_context()` 같은 조회 함수도 없다). 서버를
고치면 재현 검증(V8)이 확인한 구성과 달라지므로 앞에 투명 프록시를 두는 쪽을
골랐다. b-server 이미지에 httpx가 없어 표준 라이브러리로만 짰다.
