## 발견

### 1. 게이트웨이 결론이 완전히 뒤집혔다 (가장 중요)

주말에 "게이트웨이가 파드 교체를 5.3배 악화시킨다"고 냈다가 하네스 결함으로
철회했다. 고친 하네스로 다시 재니 **정반대**다.

| 조건 | 달성 rps | 실패 | 성격 |
|---|---|---|---|
| 게이트웨이 경유, FailClosed | 99.9 | 20건 | 5xx, 재초기화로 복구 |
| 게이트웨이 경유, FailOpen | 99.9 | 21건 | 5xx, 재초기화로 복구 |
| 직접 경로 (대조) | 97.9 | 1,255건 | 세션 유실(400), 재초기화로 복구 |

게이트웨이가 파드 교체를 **60배 가까이 잘 흡수한다.** 세션을 종단하고 살아 있는
백엔드로 다시 잡아 주기 때문이다. `failureMode`는 변수가 아니었다(20 대 21).

**발행문 수정 필요.** 현재 "게이트웨이는 문제를 없애는 게 아니라 옮긴다"는 절이
파드 교체까지 나빠지는 것처럼 읽힌다. 스케일아웃과 파드 교체 양쪽에서 게이트웨이가
낫고, 대신 게이트웨이 자체가 새 단일 장애점이 된다는 쪽으로 고쳐야 한다.

### 2. 표의 모든 값이 바뀐다 (V3, 12셀 x 10회)

| 셀 | 기존(3회) | 10회 중앙 | 10회 범위 |
|---|---|---|---|
| 구 close r2 | 98.9 | **129.6** | 95.2 ~ 155.1 |
| 구 close r4 | 38.3 | **31.5** | 22.4 ~ 57.0 |
| 구 reuse r2 | 181.4 | **168.7** | 135.7 ~ 193.4 |
| 구 reuse r4 | 119.2 | **117.1** | 102.3 ~ 190.6 (9회) |
| 신 스펙 close r1/r2/r4 | 200.0 | 200.0 | 199.7 ~ 200.0 |
| 신 스펙 reuse r1/r2/r4 | (미측정) | 200.0 | 199.9 ~ 200.0 |

구 스펙 close r2는 기존 값보다 **31rps 높다.** 3회로는 분포의 아래쪽을 잡았던 것이다.
신 스펙은 60회 관측(6셀 x 10회) 전부 200.0에 유실 0이고 연결 방식과 무관하다.

### 3. 스티키 세션은 실제로 통한다. 다만 대가가 있다 (S1)

| 구성 | 스케일아웃 r4 | 파드 교체 |
|---|---|---|
| `sessionAffinity: None` | 26.4 rps, 유실 13,760 | 97.3 rps, 유실 2,148 |
| `sessionAffinity: ClientIP` | **200.0 rps, 유실 0** | **100.0 rps, 유실 88** |

"구 스펙이면 스티키 세션 켜면 되지 않나"에 대한 답이 나왔다. 켜면 된다.

**단서를 반드시 함께 적어야 한다.** 부하 생성기가 호스트 한 대라 클라이언트 IP가
하나다. `ClientIP` 친화도는 IP 단위로 고정하므로 트래픽 전부가 파드 하나로 몰렸다.
세션이 100% 살아남은 것은 부하 분산을 100% 포기한 결과다. 실제 환경은 클라이언트
IP가 여러 개라 효과가 부분적이다.

### 4. 핸들 설계는 파드 교체에서도 갈린다 (V4)

| 설계 | 달성 rps | 핸들 유실 |
|---|---|---|
| 파드 메모리 | 53.4 | 13,942 |
| HMAC 서명 | 100.0 | 0 |
| Redis | 100.0 | 0 |

파드가 죽으면 그 파드의 상태가 전부 사라지는 가장 극적인 경우인데, 자기 보관형과
외부 저장은 영향이 없다.

### 5. Redis가 죽어도 거의 버틴다 (V5)

Redis 파드를 실행 중에 죽이면 91.7rps에 핸들 유실 24건이다(정상일 때 100.0, 0건).
"외부 저장은 새 의존성을 들이는 선택"이라는 서술은 맞지만, 재기동이 빨라 손실이
작다. 정직한 반대편을 수치로 보일 수 있게 됐다.

### 6. 30분 연속에서도 신 스펙은 유실 0 (V7)

| 조건 | 성공 | 세션 유실 | 버려짐 |
|---|---|---|---|
| 신 스펙 close r4 | 286,724 | 0 | 73,276 |
| 구 스펙 reuse r4 | 321,922 | 38,043 | 0 |

신 스펙의 달성 rps가 159.3으로 낮은 것은 **서버가 아니라 부하 생성기 쪽 한계다.**
30분 동안 호출마다 새 연결을 여느라(재연결 286,724회) 목표 틱의 20%를 못 보냈다.
서버 실패는 0이다. 구 스펙은 연결을 재사용해 틱은 다 보냈지만 38,043건을 잃었다.

### 7. nftables에서도 거동이 같다 (S2)

kube-proxy를 nftables 모드로 바꿔도 구 스펙 26.3rps(iptables 31.5와 같은 범위,
유실 13,747), 신 스펙 200.0rps 유실 0이다. 세션 유실은 데이터플레인 구현이 아니라
연결 단위 분배라는 성질에서 온다는 것이 확인됐다.

### 8. 동시성을 바꿔도 달라지지 않는다 (T2, 구 스펙만 유효)

구 스펙 레플리카 4에서 동시성 4, 8, 16, 32의 중앙값이 각각 32.7, 32.2, 24.9, 28.8이다.
뚜렷한 경향이 없다. 우리 수치가 특정 클라이언트 모양의 산물이 아니라는 방증이다.
신 스펙 쪽은 mcp-b가 죽어 있어 무효다.

### 9. 재현 검증이 실패했고, 그것이 발견이다 (V8)

문서에 적은 순서(기동 → 스냅샷 복원 → 이미지 빌드/적재 → 배포)대로 돌렸는데
이미지 빌드에서 멈췄다. 로그 원문은 `Cannot connect to the Docker daemon`이다.
colima가 꺼져 있었다.

**발행문이 이 전제를 안 밝히고 있다.** "빌드해 적재한다"고만 하고 Docker 데몬이
떠 있어야 한다는 말이 없다. 이 프로젝트 문서에 8/3에도 같은 함정이 기록돼 있는데
그때는 사람이 알아채고 켰다. 무인으로 돌리니 그대로 멈췄다.

재현 절에 한 줄 추가가 필요하다. 그리고 `deploy.sh`나 `build_and_load.sh`가 데몬을
먼저 확인하도록 고치는 편이 낫다.

## 실패와 미실행

- **S3 (경로 b, Gateway API 구현체)**: nginx Gateway Fabric을 설치했으나 Gateway
  주소를 못 받아 건너뛰었다. 원인 미확인. 한계 절의 "측정하지 않았다"는 그대로 남는다.
- **V8 (재현 검증)**: 위 9번. 실패 자체가 발견이지만 재현 확인은 못 했다.
- **T3 (30분 창 8회), T1 (워커 3대)**: V8 실패로 mcp-b가 없는 상태에서 돌아 무효.
- **V6 (레플리카 6)**: 워커 CPU 부족으로 파드가 안 떠 건너뜀. 예상했던 실패다.
- **G1~G5 (agentgateway 스파이크)**: 같은 이유로 게이트웨이가 안 떠 미실행.
